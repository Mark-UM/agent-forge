# 2.0 Lightweight Multi-Agent Kernel Acceptance Matrix

Status: planning contract. The Kernel is not implemented, and no row in this
matrix is evidence of completion until the named test and evidence exist for the
same candidate commit.

This matrix defines the minimum traceable acceptance surface for 2.0. It does
not replace detailed tests, Windows workflow logs, or local-only Provider
acceptance. Test counts alone are never release evidence.

## 1. Evidence rules

- Every blocking row must have machine-readable evidence tied to the exact
  branch head under review.
- Unit and contract evidence may run on all supported CI environments, but
  Windows remains the release platform.
- End-to-end and Windows release-smoke evidence must use Python 3.11.
- Local-only Provider checks use local credentials and private state and must
  never upload Secrets, prompts, private Memory, Browser profiles, or raw
  Provider payloads.
- A skipped blocking test is not a pass unless the requirement explicitly
  defines an optional capability and the Kernel reports it as unavailable or
  degraded.
- Failure injection must prove truthful failure semantics, not merely exercise
  an exception branch.
- Evidence must distinguish the synthetic pull-request merge ref from the
  actual branch or `main` commit being tested.

## 3. First end-to-end Task

The first 2.0 end-to-end fixture is deliberately small and deterministic:

- one simple single-file, text-only maintenance Task;
- no Secret and no private user data;
- no network write and no external Provider requirement;
- a temporary isolated Workspace, never `main`;
- Coordinator validates and plans the work;
- Worker changes only the authorized file through a bounded Workspace tool;
- combined Reviewer/Tester checks exact content, path, digest, provenance, and
  absence of unrelated changes;
- one reviewed Artifact is registered;
- Task reaches a truthful terminal state;
- no commit, push, PR readiness change, or merge occurs automatically;
- Vision is not used;
- a deterministic Gateway stub supplies typed responses and usage data.

Minimum happy-path evidence:

1. original and resulting file digests;
2. Task, AgentSpec, Handoff or Agent-as-tool, Artifact, Approval, and budget
   records as applicable;
3. one correlated Run/Step/Event tree;
4. Reviewer/Tester acceptance;
5. exact Workspace diff containing only the expected file;
6. process/port cleanup result;
7. proof that no direct model endpoint, Secret, or GitHub write was used.

The E2E suite must also include at least one Reviewer rejection/rework path, one
budget exhaustion path, one cancellation/timeout path, one duplicate-execution
attempt, and one restart-boundary scenario.

## 4. Proposed 2.0 release gate

This section defines the future gate; this planning change does not modify any
Workflow.

A 2.0 release candidate is acceptable only when one exact candidate commit has:

1. Python compilation success;
2. strict Registry validation;
3. Model Gateway no-bypass success;
4. all blocking Kernel unit, contract, and integration rows passing;
5. the deterministic single-file E2E passing, including failure injections;
6. the complete existing Windows pytest suite passing without unhandled thread
   exceptions;
7. a clean Windows Vendor/Chromium/Browser/Scheduler/Supervisor smoke plus Kernel
   process/port cleanup;
8. machine-readable JUnit/JSON evidence and a generated human-readable report
   tied to the exact commit and Actions run;
9. no unreviewed production framework dependency beyond the one selected by the
   accepted ADR;
10. documentation updated to distinguish implemented behavior from later 2.1+
    durable execution;
11. local-only Provider acceptance recorded separately for any Provider claimed
    ready, with optional Provider failures represented truthfully;
12. an explicit human review confirming that no autonomous `main` modification
    or merge path was introduced.

A previous green commit, a hand-written test count, a generic framework demo, or
an unavailable blocking test is not release evidence.
