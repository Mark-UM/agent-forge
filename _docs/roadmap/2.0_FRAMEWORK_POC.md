# 2.0 Framework PoC Evaluation Plan

Status date: 2026-08-06.

This document designs two equivalent proofs of concept. It does not execute a
PoC, install a package, modify dependencies, select a framework, or authorize
production adoption.

## 1. Candidates and official-source snapshot

Only first-party documentation and repositories are valid sources for technical
claims in this evaluation. The snapshot was reviewed on **2026-08-06**.

| Candidate | Official package/repository snapshot | Python/license baseline |
|---|---|---|
| OpenAI Agents SDK | `openai/openai-agents-python`, latest release `v0.19.4` published 2026-08-05 | official `pyproject.toml`: Python `>=3.10`, Python 3.11 classifier, MIT |
| PydanticAI | `pydantic/pydantic-ai`, latest release `v2.25.0` published 2026-08-06 | official `pyproject.toml`: Python `>=3.10`, Python 3.11 classifier, MIT |

Official materials indicate that both candidates expose Agent/tool abstractions,
typed output support, MCP integrations, model/provider extension points, usage
or telemetry surfaces, and active maintenance. Those facts justify measured
PoCs; they do not establish Agent Forge compatibility.

Before a PoC branch is created, repeat the official-source snapshot and record:

- exact release tag and commit;
- package metadata and transitive dependency lock;
- Python and Windows support statements/tests;
- license files;
- official documentation pages used for every evaluated feature;
- changes since this planning snapshot.

Star count, brand familiarity, community impressions, and generic tutorials are
not decision evidence.

## 2. Non-negotiable Agent Forge boundary

A candidate passes only if it can remain behind a thin, replaceable Adapter:

```text
Kernel domain contracts
        |
Framework Adapter
        |
modules.dispatch.gateway  <--- sole model policy/endpoint owner
        |
Provider transport

Kernel tool Adapter -> existing MCP/Search/Browser/Memory/Scheduler boundaries
Kernel telemetry Adapter -> existing Run/Step/Event
Kernel Task repository -> Agent Forge SQLite Task/checkpoint authority
```

The framework must not:

- construct or own production DeepSeek/OpenAI-compatible endpoints outside the
  Gateway;
- receive raw production Secrets when a bounded Gateway callback suffices;
- make its session/checkpoint database the Task authority;
- force remote tracing or capture raw prompts/responses;
- replace existing MCP, Search, Browser, Scheduler, Memory, Registry, Runtime,
  or Run/Step/Event contracts;
- require its Agent/Run/Handoff objects to become persisted domain types;
- multiply Gateway retry, timeout, token, or cancellation policy;
- require the unselected framework in production dependencies.

Failure of any hard boundary removes the candidate regardless of feature count.

## 3. Evaluation dimensions

Each candidate receives the same evidence template. Every claim is classified as
**pass**, **pass with Adapter**, **gap**, **fail**, or **not measured**.

| Dimension | Evidence required |
|---|---|

| License | first-party license file and package metadata compatible with the project |
| DeepSeek/OpenAI-compatible Provider | demonstrate a Gateway-backed model Adapter; framework never owns the production endpoint |
| Gateway uniqueness | static scan and call trace prove every model request traverses `modules.dispatch.gateway` |
| MCP | connect to the same deterministic MCP/tool stub; measure lifecycle, schemas, cancellation, errors |
| Tool calling | typed arguments/results, allowlist enforcement, validation, failure mapping, bounded output |
| Agent-as-tool | caller retains Task ownership; child usage and errors map once |

## 4. Functionally equivalent PoC scenario

Both PoCs implement exactly the same text-only scenario on isolated experimental
branches or temporary workspaces. Neither is a production implementation.

### Roles

- **Coordinator:** receives one normalized maintenance objective and chooses a
  direct action or one Worker assignment.
- **Worker:** edits one permitted text file through a deterministic Workspace
  tool and returns a typed proposed Artifact.
- **Reviewer/Tester:** checks exact expected content, path, digest, provenance,
  and absence of unrelated changes; returns accept or bounded rejection.

### Scenario

1. Create a Task with the same IDs, normalized input, AgentSpecs, permission
   scope, initial budgets, and deterministic idempotency keys.
2. Coordinator produces the same typed one-step plan.
3. Worker calls the same MCP/tool stub to modify one temporary file.
4. Worker returns the same Artifact contract.
5. Reviewer/Tester evaluates the same acceptance criteria.
6. The Adapter emits the same normalized execution result, usage, errors, and
   Run/Step/Event sequence.
7. No commit, push, PR mutation, or merge occurs.

### Shared stubs

Both candidates must use identical framework-neutral stubs:

- **DeepSeek Gateway stub:** implements only the Adapter-facing Gateway protocol;
  returns deterministic typed model outputs, usage, latency, retryability, and
  normalized errors. It exposes no real API key and makes no network call.
- **MCP/tool stub:** exposes one read and one bounded write operation against a
  temporary Workspace; records arguments, result, cancellation, and call count.
- **Task repository stub or temporary SQLite repository:** uses the same project
  contracts and remains authoritative outside the framework.
- **Telemetry sink:** captures the same Run/Step/Event contract and rejects raw
  prompt/response or Secret-like metadata.

### Same budgets

Use one frozen Budget fixture for both candidates, including:

- maximum logical steps;
- input/output/total token limit;
- wall-clock deadline;
- retry limit;
- tool-call limit;
- Agent count;
- child-Task count.

Charging boundaries and expected remaining values are precomputed before either
implementation. Framework-native retries or hidden model calls count against the
same limits and are treated as negative evidence when they cannot be controlled.

### Same failure injection

At minimum, run:

1. model validation failure;
2. required Provider unavailable from Gateway stub;
3. MCP/tool exception;
4. Worker timeout;
5. parent cancellation during Worker execution;
6. Reviewer rejection followed by one bounded retry;
7. token exhaustion before the next model call;
8. retry exhaustion;
9. duplicate Handoff/tool idempotency key;
10. telemetry sink failure;
11. temporary SQLite lock/write failure;
12. malformed typed output.

Expected normalized outcome is fixed before the PoCs. A framework-specific
exception class is never the acceptance result.

### Environment

- Windows release environment;
- Python 3.11;
- clean, separate virtual environment per candidate;
- same hardware and power state where practical;
- same repository baseline and PoC harness;
- cold and warm measurements;
- no real Secret, remote trace, Search/Browser network, or private Memory;
- no SiliconFlow Vision dependency.

## 5. Required assertions

Both PoCs must prove:

- identical happy-path Task, Artifact, review, and terminal result;
- identical external ownership semantics for Agent-as-tool and explicit Handoff;
- no direct model endpoint or framework-owned production client;
- one Gateway invocation per planned model operation unless the frozen scenario
  explicitly requires more;
- no hidden/unbounded retry loop;
- cancellation and timeout leave no running Agent/tool task;
- typed validation failures map to the same project category;
- MCP/tool permissions are enforced before side effects;
- Task/checkpoint state remains in the project repository;
- Run/Step/Event correlation contains no raw sensitive content;
- the framework can be disabled or removed without changing persisted domain
  records or the deterministic reference tests.

## 6. Measurements

Record raw and summarized measurements for every candidate.

### Dependency and startup

- direct dependencies and enabled extras;
- full locked transitive dependency count;
- download and installed size;
- conflicts or changed versions relative to Agent Forge lock;
- cold `import` time over repeated fresh processes;
- warm import time;
- time to construct Agents/tools and first deterministic run;
- startup variance and Windows-specific warnings/errors.

### Runtime resources

- baseline process RSS before import;
- post-import idle RSS;
- peak RSS during happy and failure paths;
- created threads, subprocesses, sockets, and event loops;
- cleanup time and residual process/port state.

### Adapter complexity

- new production Adapter lines and files;
- framework-specific branches or workarounds;
- number of project contracts translated;
- custom model Provider implementation required;
- tool/MCP wrapping complexity;
- cancellation/timeout/retry glue;
- telemetry and usage glue;
- test-only code required for deterministic behavior;
- reliance on private or unstable framework APIs.

Raw line count is context, not a winner by itself. Reviewers must judge whether
the Adapter removes more first-party complexity than it adds.

### Semantic fit

- clarity of Agent-as-tool versus Handoff;
- ability to keep Handoff acceptance/idempotency in project state;
- typed output error quality;
- parent/child cancellation behavior;
- error and usage fidelity;
- streaming control;
- MCP lifecycle control;
- resistance to framework-owned state authority;
- ease of mapping to Run/Step/Event;
- Windows test repeatability across repeated runs.

## 7. Candidate-specific questions

### OpenAI Agents SDK

The PoC must answer with official APIs and measurements:

- Can a custom model implementation call the existing Gateway without exposing
  the framework's default endpoint/client path?
- Can model/provider retries and tracing be disabled or controlled precisely?
- Do Agent-as-tool and Handoff semantics map cleanly to project ownership rules?
- Can MCP tool schemas, cancellation, and errors be wrapped without framework
  sessions becoming authoritative?
- Can usage and streaming events be captured without raw content leakage?
- Are session features optional, and can project SQLite remain the only Task
  authority?
- What core and optional dependencies are actually needed for this scenario?

### PydanticAI

The PoC must answer with official APIs and measurements:

- Can a custom/wrapper model call the existing Gateway while preserving typed
  messages/results and usage?
- Can model retries, tool retries, and graph behavior be made subordinate to
  project budgets?
- Is explicit Handoff best represented by Agent delegation, tool invocation, or
  a project-owned state transition outside the framework?
- Can MCP/toolsets be used through the same permission and cancellation Adapter?
- Can Logfire or other telemetry be fully disabled/replaced by local
  Run/Step/Event without hidden export?
- Can project SQLite remain authority rather than graph/history persistence?
- Is `pydantic-ai-slim` with selected extras sufficient, and what dependency
  difference results versus the default package?

## 8. Scoring and hard Gates

Scores guide review but cannot override a hard failure.

Suggested weighted categories:

| Category | Weight |
|---|---:|
| Gateway, authority, security, and privacy fit | 30% |
| cancellation, timeout, retry, error, and budget semantics | 20% |
| Agent-as-tool, Handoff, typed output, and MCP fit | 15% |
| deterministic Windows testing and stability | 15% |
| Adapter complexity and replaceability | 10% |
| dependency/startup/memory cost | 5% |
| maintenance/license/documentation | 5% |

Score each item from 0 to 4 and attach evidence. The following are hard Gates:

1. Python 3.11 clean Windows execution.
2. Compatible license.
3. `modules.dispatch.gateway` remains the only production model policy/endpoint
   owner.
4. No framework-owned Task/checkpoint authority.
5. Remote/sensitive tracing can be disabled.
6. Finite cancellation, timeout, retry, and budget behavior can be imposed.
7. MCP/tool permissions and Workspace/network boundaries remain enforceable.
8. Domain contracts and SQLite records stay framework-neutral.
9. Equivalent deterministic tests pass without real Secrets.
10. The Adapter is sufficiently thin and uses supported public APIs.

A candidate failing a hard Gate is not eligible even if its weighted score is
higher.

## 9. Formal decision rule

- Select **one** primary production framework at most.
- The other candidate does not enter production requirements or lock files.
- Every framework model call passes through a Model Gateway Adapter; the
  framework never owns the production endpoint.
- Agent Forge Task/checkpoint SQLite remains authoritative.
- A thin self-owned Kernel with no orchestration framework is an allowed result
  when neither candidate provides a clear, measured reduction in complexity or
  capability risk.
- No selection is made from popularity, feature-list breadth, or a single happy
  path.
- The decision requires an independent ADR containing official-source snapshot,
  reproducible PoC commits/environments, raw measurements, hard-Gate results,
  weighted comparison, migration/removal cost, security review, and dissenting
  risks.
- This planning PR makes **no final framework selection**.

## 10. PoC exit criteria

The PoC phase is complete only when:

- both candidates run the same committed harness and frozen fixtures;
- all required happy/failure assertions have results rather than assumptions;
- measurements are repeated and include variance;
- direct/transitive dependencies and license evidence are captured;
- Windows Python 3.11 cleanup is verified;
- Gateway/no-bypass and Task-authority boundaries are proven;
- unknowns and unsupported features are marked explicitly;
- an ADR recommends OpenAI Agents SDK, PydanticAI, or the thinner self-owned
  Kernel;
- reviewers approve the ADR before Slice 5 changes production dependencies.
