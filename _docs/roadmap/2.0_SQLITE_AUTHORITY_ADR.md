# ADR: 2.0 Kernel Task and Checkpoint SQLite Authority

- **Status:** Accepted for the Slice 1 implementation candidate.
- **Decision date:** 2026-08-06.
- **Scope:** Task identity, state, claims, idempotency, and checkpoints.
- **Not selected here:** Agent framework, Coordinator policy, Workspace executor, or 2.1 recovery engine.

## Context

Agent Forge already has authoritative state for Scheduler jobs/runs, Search
cache, Memory candidates, Runtime Supervisor ownership, private Memory, and the
Browser profile. The 2.0 Kernel needs a separate Task/checkpoint authority
without turning Run/Step/Event telemetry or an existing capability store into a
second orchestration database.

The authority must be Windows-first on Python 3.11, add no dependency in Slice
1, prevent duplicate execution, and commit state plus checkpoint changes
atomically. Ordinary direct CLI, MCP, and tool calls remain independent from the
Kernel.

## Decision

Use a dedicated SQLite database:

```text
_runtime/kernel/kernel.db
```

The first schema owns only:

- `kernel_schema_migrations`;
- `kernel_tasks`;
- `kernel_task_checkpoints`.

`modules.kernel.TaskRepository` is the public API and the private
`modules._kernel.repository.TaskRepository` implementation is the only
first-party writer for these tables. Tests may inject another path.

The repository provides:

- explicit transactions and rollback;
- foreign-key enforcement, WAL, a bounded busy timeout, and normal synchronous
  mode;
- a schema version and checksum, with unknown future versions rejected;
- unique `(idempotency_scope, idempotency_key)` request identity;
- a canonical request digest that distinguishes safe replay from conflicting
  reuse;
- optimistic compare-and-set through `record_version`;
- one transaction for each state update and checkpoint insert;
- bounded claim tokens and expiry;
- explicit lease renewal only while a claim remains live;
- no automatic replay after uncertain work.

Persisted values are framework-neutral JSON and scalar fields. Raw prompts,
model responses, Secrets, private Memory, framework sessions, and arbitrary
Python serialization are prohibited.

## Authority boundaries

This database does not replace, migrate, mirror, or directly write:

| Existing domain | Existing authority retained |
|---|---|
| Scheduler jobs and attempts | Scheduler tables in `_runtime/mcp-sqlite.db` |
| Search result/provider cache | Search cache authority |
| Memory candidates | Memory candidate tables |
| Durable private Memory | `_data/memory/*.md` |
| Runtime service ownership | `_runtime/supervisor/state.json` |
| Browser cookies and storage | ignored Browser profile |
| Operational telemetry | existing Run/Step/Event model |

A Task may reference an external `run_id`, but references do not transfer
authority. Cross-domain actions require explicit adapters and idempotency keys;
long-term dual writes are prohibited.

## Why a separate physical file

Putting Task tables in `_runtime/mcp-sqlite.db` would couple Kernel migrations,
lock contention, backup, restore, corruption scope, and rollback to
Scheduler/Search/Memory. The dedicated file gives the new authority a clear
lifecycle while retaining SQLite's local simplicity.

A later consolidation requires a separate ADR, migration and rollback plan,
release evidence, and proof that one authority per state domain remains intact.

## Alternatives rejected

- **Scheduler jobs/runs:** trigger authority is not Task, Handoff, Artifact,
  Approval, budget, or checkpoint authority.
- **Run/Step/Event:** observability must describe Kernel work without becoming
  mutable recovery state.
- **Framework session store:** no framework has been selected, and production
  state must remain replaceable behind a thin Adapter.
- **JSON files:** they do not safely provide multi-record transactions,
  uniqueness, compare-and-set, foreign keys, or concurrent claims.

## Registry boundary for Slice 1

Slice 1 exposes a thin import surface at `modules.kernel`. Its implementation
lives in `modules._kernel`, which the existing Registry intentionally treats as
private. This avoids advertising an executable Kernel capability before a
Coordinator or canonical lifecycle exists. A later implementation slice must
add a normal `modules/kernel/manifest.json` and update Registry inventory when
there is a real production entry point to register.

## 2.0 and 2.1 boundary

Slice 1 persists committed Task state and checkpoints. It does not promise safe
replay of an in-flight file, subprocess, network, model, or external-service
side effect. An expired claim is not silently reclaimed as though no work
occurred; the Task requires explicit reconciliation and may become `abandoned`.

Durable Workspace materialization, process recovery, pause/resume,
latest-valid-checkpoint replay, and bounded rollback remain 2.1 work.

## Merge evidence

The exact candidate commit must pass:

- typed-contract and state-machine tests;
- identical idempotent replay and conflicting-key rejection;
- stale-writer and concurrent-claim rejection;
- claim-token, expiry, renewal, and checkpoint-redaction tests;
- state/checkpoint rollback on checkpoint failure;
- schema version/checksum checks;
- Windows database-handle cleanup;
- Python compilation, strict Registry validation, Model Gateway no-bypass;
- complete existing CI and Windows release smoke.
