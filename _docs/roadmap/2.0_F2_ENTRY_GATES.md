## Contract gate

The merged F1 seam in [PR #9](https://github.com/Mark-UM/agent-forge/pull/9)
validates protocol v1, health, capabilities, request correlation, bounded
events, and cancellation. The next Kernel slice adds a persisted
`WorkspaceBinding` (logical ID, canonical root, filesystem identity) to Task
and checks it before Executor invocation. Bound Task file Artifact operations
fail closed until a handle-safe or OS-isolated access path exists; a path check
followed by a separate file open has a replacement race. Its v2 Task schema
migrates existing v1 rows with a null binding. The fixed-Provider demo passes
the binding into its launcher. This
does not make the demo an isolated production Executor. Before passing a real
AgentCommand to MyHarness, the contract must additionally specify and validate:

1. a read-only path set and explicit Workspace selection by a trusted Kernel
   entry point, rather than by task input;
2. a unique external attempt identity and durable idempotency/replay policy;
3. finite wall time, turns, tool calls, context, output bytes, retries, and
   child-agent limits, rejecting dimensions the Adapter cannot enforce;
4. event byte/count caps, unknown-event handling, terminal ordering, and
   cancellation precedence under process exit and late output;
5. explicit tool/permission subset, with no write, network, Git, subprocess,
   private Memory, or independent Provider credential in the PoC.

These items can be implemented incrementally. An isolated source or CLI probe
does not by itself prove the Kernel request mapping or authorize a production
Bridge.

The v1 to v2 schema change is additive and runs in a SQLite transaction. On
failure, the transaction rolls back. Before upgrading an existing live DB,
stop Kernel writers and take a SQLite backup including committed WAL content.
Restore that backup if the upgrade fails or if rollback is needed before any
post-upgrade writes. If bound Tasks have been created, a downgrade needs an
explicit data migration plan; do not discard `workspace_json` or silently
replay them as unbound Tasks.

## OS isolation gate

`--mode json` controls output format; `--tools`, `--no-tools`, and
`--no-extensions` are CLI selection controls. None is an OS write boundary.
The experiment must use a disposable Workspace mounted or ACL-enforced as
read-only, an inaccessible outside sentinel, a sanitized environment, and no
production credential, private data, or host repository write access. Network
must be disabled for the fixed Provider fixture. Record before/after file and
process inventories. Limit stdout/stderr bytes, wall time, and the owned
process tree; verify cancel and timeout leave no descendants.

On the current host, Docker and Podman commands were absent. The Windows
edition registry reports `CoreCountrySpecific` (Home China), for which
[Windows Sandbox is unsupported](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-overview).
The restricted shell initially denied WSL access, but the authorized host
context could run WSL2 Ubuntu. Its installed `bubblewrap` completed a minimal
`--unshare-all` launch with only selected Linux system directories bound, and
the guest could not see `/mnt/c`. That initial containment check alone was
not a MyHarness safety proof. The later exact-SHA CLI probe below added native
Linux Node, a read-only source bind, network and host interop denial, and a
sanitized environment; it exposed a platform startup failure before JSONL.
The remaining sentinel and process-cleanup matrix is still required. Do not
substitute a writable temp directory plus CLI flags for this boundary.

official native Linux Node v22.22.1 archive matched its published SHA-256,
`9a6bc82f9b491279147219f6a18add1e18424dce90d41d2a5fcd69d4924ba3aa`.

TMPDIR, and a network connection failed with no route. The verified source
checkout remained clean.

The first `--mode json --no-session --no-tools --no-extensions --offline`
probe with a fixed local Provider exited before emitting a JSONL session
header. The CLI creates `CodeIntelligenceRuntime` even with no tools. Its
[path semantics](https://github.com/Mark-UM/MyHarness/blob/5be723be1b5c34cae2abe6fea5718f0407f91760/packages/coding-agent/src/symbols/path-semantics.ts)
use `node:path.win32` on every platform, converting the Linux Workspace
`/work` to `\work`; `statSync` then raises `InvalidWorkspaceRootError`
(`ENOENT`). The unconditional construction is in
[session services](https://github.com/Mark-UM/MyHarness/blob/5be723be1b5c34cae2abe6fea5718f0407f91760/packages/coding-agent/src/agent/runtime/services.ts).
The fixed Provider was not reached. This is a runtime platform mismatch at the
exact pin, not a JSONL or Provider result. No file in the pinned source or
Agent Forge was changed to bypass it.

F2 remains blocked for the current Linux sandbox. Resume only with an
OS-isolated Windows execution environment for this exact SHA, or with a
reviewed MyHarness path fix and a newly verified SHA/pin. Re-run source,
license, sandbox, and failure-matrix checks for either route. CLI success
must not be inferred from the build or `--version` result.

## Windows startup experiment

The `agent/f2-windows-probe` branch adds an experimental GitHub-hosted Windows
runner job for the exact candidate commit, a fixed local Provider, and no tools.
It uses a disposable VM, does not persist checkout credentials, and starts the
CLI with a reduced child environment, 30-second timeout, and 128 KiB streaming
output limit. On exact head `4efedcd9abbe7521a52a9ad8130f9e6b930c6cba`,
the [Windows startup run](https://github.com/Mark-UM/agent-forge/actions/runs/36399417956)
passed: 20 JSONL events, 6296 output bytes, a `session` v3 header,
`agent_end`, the fixed Provider response, and zero tool execution events.
This confirms CLI compatibility on this Windows runner, not F2 isolation.

The same branch adds `scripts/experiments/kernel_myharness_vertical.py`, which
runs one fixed no-tool Task through `KernelExecutionEngine` and the F1 Executor
seam into the JSONL launcher. The Node launcher extracts the final assistant
message and enforces a streaming output cap. On exact head
`e44a03bf85f4fd8f91497103a329526b0b7c8882`, the
[Windows vertical run](https://github.com/Mark-UM/agent-forge/actions/runs/36402086795)
passed: `taskStatus=succeeded`, `executorProtocol=1`, and
`result=F2_FIXTURE_SUCCESS`. This is a working, explicitly invoked demo, not
the production Bridge.

The experiment merged in [PR #12](https://github.com/Mark-UM/agent-forge/pull/12)
at `f69a99b8c807d89a156268c3fbd6940641545215`. Its
[main workflow dispatch](https://github.com/Mark-UM/agent-forge/actions/runs/36404444179)
passed: 20 JSONL events, fixed response, zero tool execution events, and Kernel
Task `succeeded`. The merge commit's CI, Capability, Gateway, and Windows
release workflows also passed. A separate local Windows run with Node 22.22.1,
Python 3.11.9, and the exact source pin passed both startup and Kernel paths.

This process-boundary iteration adds a bounded JSONL parser/supervisor and
Windows tests for missing executable, malformed/unknown events, terminal order,
tool execution, missing fixed output, crash, streaming overflow, timeout, and
cancellation. A synthetic descendant test checks Windows process-tree cleanup
on timeout. These child tests cover the launcher boundary; they do not prove
OS-level read-only Workspace or network isolation. Full F2 acceptance still
requires the external sentinel, actual CLI process-tree, and sandbox evidence
below.

This startup job does not enforce a read-only Workspace or network denial, does
not capture complete before/after file and process inventories, and exercises
only the launcher's synthetic subset of the failure matrix below. The complete
matrix against the actual CLI under OS isolation remains open. A passing run
does not close the F2 OS isolation gate, prove the full Executor contract, or
authorize an F3 Bridge. Record the exact workflow run for each iteration. The
two earlier Windows
attempts built the exact source but stopped before CLI launch: the first at an
unreachable network positive control, the second at Windows `Start-Process`
with alternate credentials. Neither attempt established MyHarness JSONL behavior.

## PoC acceptance sequence

1. Verify the chosen source commit/tree and license/notices again in the
   actual sandbox, then install dependencies from the lock with lifecycle
   scripts disabled until their effects have been reviewed. Record Node,
   package-manager, dependency, and build outputs.
2. Prove a no-tool fixed Provider fixture runs without external credentials or
   network. Then enumerate the exact pinned `read`, `grep`, `find`, `ls`, and
   `symbols` implementations; enable only verified read operations.
3. Parse the JSONL session header and permitted events with strict size,
   sequence, and terminal checks. Treat event text as untrusted data, never as
   an instruction or Task authority.
4. Exercise success, missing executable/SHA mismatch, malformed JSON, unknown
   event, crash, timeout, cancellation, output overflow, disallowed tool, and
   attempted outside write. For every case capture exit code, bounded output,
   event/Task mapping, unchanged sentinel, and process cleanup evidence.
5. Only after the matrix passes may F3 evaluate the SDK Bridge. Production
   Provider routing, mutable Workspace access, and Artifact registration have
   separate later gates in the [Fusion ADR](../adr/MYHARNESS_EXECUTOR_ADR.md).
