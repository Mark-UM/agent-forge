# ADR: Slice 2 bounded Coordinator/Worker execution

- **Status:** Accepted for the Slice 2 implementation candidate.
- **Decision date:** 2026-08-06.
- **Scope:** deterministic Coordinator/direct/Worker-as-tool execution only.
- **Excluded:** explicit Handoff, Artifact/Approval repositories, Reviewer,
  framework Adapter, live Provider, durable Workspace recovery, and autonomous
  GitHub writes.

## Decision

Slice 2 adds a framework-neutral execution loop in `modules.kernel.execution`.
The Coordinator always remains the authoritative Task owner. A Worker is invoked
as a bounded typed tool and returns control to the Coordinator; no ownership
transfer occurs. The only future mechanism allowed to transfer ownership is the
persisted Handoff implemented in Slice 3.

The loop accepts injected `AgentRuntime` implementations. Production model
transport is not implemented here, no Provider endpoint or Secret is accepted,
and the deterministic runtime used by tests performs no network request.

## Deterministic planning

For the same Task, AgentSpecs, readiness set, permissions, budget, and direct
preference, allocation is stable:

1. use the Coordinator directly when it is ready and satisfies the complete
   contract;
2. otherwise inspect Workers in `agent_id` order;
3. select the first ready Worker satisfying capability, input, permission, tool,
   and AgentSpec budget constraints;
4. fail truthfully when no Agent is eligible.

No fallback widens permissions or constructs a direct model client.

## Authorization boundary

Before an Agent runtime is called, the Kernel verifies:

- required capabilities are declared by the selected AgentSpec;
- a requested tool exists in both AgentSpec and PermissionScope allowlists;
- Workspace paths are project-relative, non-escaping, and inside an allowed root;
- requested network, subprocess, private-Memory, and Git-write permissions are
  explicitly present;
- required input fields are present;
- the selected AgentSpec can contain the Task budget.

A denial invokes no Agent runtime and creates no tool side effect.

## Budget boundary

Slice 2 enforces finite structural accounting for:

- one Coordinator planning step;
- one direct or Worker execution step;
- one or two participating Agents;
- one tool call when a command names a tool;
- deterministic runtime token, wall-clock, and retry usage.

The engine rejects the next operation before invocation when structural budget
is exhausted. Agent runtime usage must fit the remaining command budget. Full
parent/child reservation, transfer, retry composition, and Gateway usage
reconciliation remain Slice 4.

## State and telemetry

`TaskRepository` remains the only Task/checkpoint writer. Execution claims a
queued Task once and commits one truthful terminal transition. Terminal
checkpoint payloads contain the correlated `run_id`, plan IDs, selected Agent,
status, bounded usage, output keys, and an output digest. They do not contain raw
Agent output, prompts, model responses, framework sessions, or Secrets.

Run/Step/Event remains telemetry, not authority. Runs use `kernel.task`, include
`task_id`, owner, execution mode, selected Agent, and attempt metadata, and map
success, degraded, failure, timeout, and cancellation to the Task outcome.
Because the existing canonical Run taxonomy represents cancellation as
`abandoned`, the Run metadata retains the exact Task terminal state
`cancelled`; the Task SQLite state remains authoritative.

A queued cancellation transitions directly from `queued` to `cancelled` without
a claim or Agent invocation. A running cancellation is cooperative. A timeout is
distinct from cancellation and generic execution failure.

## Duplicate execution and crash boundary

A Task that is not queued is never re-executed by this loop. SQLite claim/CAS
conflicts become deterministic duplicate-execution errors, and a terminal Task
cannot repeat the Agent runtime side effect.

Slice 2 does not transparently replay uncertain in-flight side effects. Crash
reconciliation and durable Workspace replay remain the documented 2.1 boundary.

## Legacy compatibility

Existing CLI, OpenCode, MCP, Search, Browser, Scheduler, Memory, and other direct
single-Agent/function paths are unchanged. Kernel execution is opt-in and adds
no new entry point, dependency, Workflow, or persistent state domain.

## Required evidence

The exact candidate head must pass:

- deterministic direct and Worker assignment;
- Coordinator ownership during Agent-as-tool;
- capability, input, Workspace, tool, and permission denial before side effect;
- success, degraded, failure, queued/running cancellation, and timeout mapping;
- structural budget exhaustion and bounded runtime usage;
- duplicate execution with one Agent invocation;
- result digest/checkpoint redaction and exception-message sanitization;
- Kernel Manifest, compilation, strict Registry, Model Gateway no-bypass;
- complete Windows tests and clean Windows release smoke.
