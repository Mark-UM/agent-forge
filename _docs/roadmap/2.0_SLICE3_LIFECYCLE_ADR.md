# Agent Forge 2.0 Slice 3 Lifecycle Authority ADR

Status: implemented candidate for review.

Date: 2026-08-06. Amended: 2026-09-26 (resolved protected-path validation).

## Decision

Slice 3 adds framework-neutral persisted Handoff, Artifact, Approval, and append-only domain-audit records to the existing Kernel SQLite authority at `_runtime/kernel/kernel.db`.

`LifecycleRepository` extends `TaskRepository`. A lifecycle operation that changes Task ownership or waiting state updates the lifecycle record, authoritative Task row, and Task checkpoint in one SQLite transaction. Run/Step/Event references remain observability metadata; they do not become a second state authority.

## Schema ownership and migration

The existing Task/checkpoint schema remains version 1 under `kernel_schema_migrations`. Slice 3 uses an independent `kernel_records_schema_migrations` ledger for:

- `kernel_handoffs`;
- `kernel_artifacts`;
- `kernel_approvals`;
- `kernel_domain_audit`.

This avoids invalidating the already-shipped Task schema checksum while retaining one physical Kernel database and one authority boundary. Startup verifies the records migration version, checksum, required tables, and exact columns. Missing or altered authority tables fail closed.

## Handoff semantics

A Handoff is ownership transfer, not Agent-as-tool.

1. The current owner creates a `requested` Handoff while holding the active Task claim.
2. The Task moves atomically from `running` to `handoff_pending`; ownership remains with the source and the execution claim is released.
3. The intended target may accept the Handoff. Acceptance alone does not transfer ownership.
4. Only `accepted -> consumed` atomically transfers Task ownership to the target and creates a new bounded claim.
5. Duplicate consumption with the same key returns the committed result; a different consumer conflicts and cannot repeat work.
6. Rejection, participant cancellation, or expiry resumes the source with a new claim.
7. Completion requires an accepted or degraded Artifact of the declared type, produced by the target and linked to the Handoff.

The Handoff stores a finite transferred-budget envelope and rejects values above the Task's remaining budget. The full reservation/release ledger and parent/child usage reconciliation remain Slice 4 by the execution plan; Slice 3 does not pretend that validation alone is complete budget accounting.

## Artifact semantics

Artifact records are immutable logical identities and never store unrestricted output bytes.

- Registration accepts an existing regular file inside one resolved Workspace root.
- Absolute paths, traversal, `.git`, Kernel authority storage, and resolved symlink/junction escape are rejected.
- Protected path checks run on both the normalized reference and the full resolved target path, using case-insensitive component matching. Internal symlink/junction aliases and reselected roots cannot expose `.git` or `_runtime/kernel` through Artifact registration or validation.
- Slice 3 accepts `workspace_root` from a trusted coordinator; it does not bind that root to a Task. The later Workspace adapter must verify the assigned root before allowing an Executor to request Artifact registration or validation. The repository's path checks do not by themselves authorize arbitrary caller-selected roots.
- SHA-256 is recomputed from materialized bytes before registration.
- Provenance requires source-input references, step references, and producer version.
- General Workspace registration accepts only `public` or `project` sensitivity; Secret/private content must use an existing approved private-storage boundary.
- Validation recomputes the digest before accepted/degraded transitions.
- Changed bytes require a new Artifact identity, an explicit predecessor ID, and the exact prior digest. The predecessor is superseded in the same transaction. Silent overwrite and orphan supersession are impossible.

## Approval semantics

Approval is a scoped decision, not a reusable role grant.

- A request stores the normalized action, action digest, exact scope, requester, expiry, and idempotency key, then moves the Task to `waiting_approval` atomically.
- `workspace.write` requires a normalized Workspace-relative target, an Artifact digest, and a scope containing only that exact target.
- One compare-and-set decides a pending request. Denial fails the Task without authorizing a side effect.
- Approval alone is not authorization. The requester must consume the exact approved action and digest before the Task resumes.
- Consumption is single-use and idempotent and returns an immutable `ApprovalAuthorization` for a future side-effect adapter.
- Expired, cancelled, denied, altered, or already-consumed approvals cannot authorize work.

Slice 3 deliberately does not add a real write, publication, credential, network, or GitHub side-effect entry point.

## Security and privacy

All persisted lifecycle metadata passes the Kernel bounded JSON and Secret-rejection boundary. Records contain references, digests, identifiers, bounded reasons, and validation evidence, not raw prompts, model responses, credentials, cookies, private Memory, or Artifact bytes.

Domain audit rows are append-only through the public repository surface. Every lifecycle transition includes the authoritative Task ID and bounded correlation data.

## Concurrency and failure behavior

All mutable records use optimistic versions. Creation and consumption have scoped idempotency keys. SQLite uses immediate transactions, foreign keys, WAL, bounded busy timeout, and rollback on any record, Task, checkpoint, or audit write failure.

Lease expiry does not imply safe replay of uncertain external side effects. That remains an explicit reconciliation boundary and does not claim 2.1 durable recovery.

## Downgrade and rollback

The Slice 3 entry surface can be disabled and its code reverted while preserving append-audited lifecycle tables. The earlier `TaskRepository` ignores the independent records ledger and remains able to read Task/checkpoint state. No automatic destructive downgrade or lifecycle-record deletion is performed.

## Excluded

- Reviewer/Tester decisions and rework loops;
- complete budget reservation, release, transfer, and Gateway reconciliation;
- real Provider or third-party framework integration;
- hard process preemption, distributed concurrency, and durable crash replay;
- end-to-end file mutation or autonomous commit, push, PR readiness, protection, or merge.
