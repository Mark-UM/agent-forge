## 3. Reorganized Implementation Strategy

The source document's 8 directions are organized by **function**. For execution, reorganize by **mechanism** — three categories with very different cost profiles:

### Category A: Prompt-Layer (lowest cost, highest leverage)

**Mechanism**: New `.md` files in `.opencode/prompts/contexts/` and `.opencode/prompts/tasks/`. Zero Python changes. Loaded automatically by `composer.py` based on `context.py` detection.

**Covers**: Direction 2 (naming-contract), Direction 5 (test-quality-gate), Direction 6 (anti-pattern-blacklist)

**Why first**: A single new `contexts/anti-patterns.md` file at `priority: 95` will be auto-loaded for every code task and immediately affect all deepseek output. No code risk, no architecture risk, immediate A/B measurable via existing `experiments.py`.

### Category B: Architecture-Layer (medium cost, structural change)

**Mechanism**: Modify `opencode.json`, refactor Flash callers in `modules/search/` and `modules/prompt/classify.py`, possibly add a `modules/dispatch/` guard.

**Covers**: Direction 4 (flash-role-guard)

**Why second**: This is the only direction that changes the model-collaboration architecture. It must be done before skills (Category C) because skills like `integration-link-checker` may themselves invoke Flash — they need the guard in place first.

### Category C: Skill-Layer (highest cost, new capabilities)

**Mechanism**: New `SKILL.md` files in `.opencode/skills/` plus supporting Python modules where static analysis is needed.

**Covers**: Direction 1 (project-bootstrap), Direction 3 (integration-link-checker), Direction 7 (ui-component-enforcer), Direction 8 (delivery-checklist)

**Why last**: Skills are the most complex to build (Direction 3 needs AST analysis, Direction 1 needs template generation, Direction 8 needs multi-check orchestration). Doing them after prompts and architecture means they're built on a disciplined foundation, not adding discipline to a leaking one.

#### 1A. Direction 6 — `anti-pattern-blacklist` prompt (P0, first)

**Rationale**: Highest leverage. Single file, loaded for every code task, immediately blocks the "explicit constraint bypass" pattern that is deepseek's most damaging habit.

**Files to create**:
- `.opencode/prompts/contexts/anti-patterns.md` — `priority: 95`, language-agnostic core rules + language-specific sections

**Content structure** (from source document Section 3.2 Direction 6):
```
---
description: Anti-pattern blacklist enforced across all code generation
priority: 95
version: 2.0.0
---
# Anti-Pattern Blacklist (enforced, no exceptions)

## Engineering Anti-patterns
- ❌ ESLint rule explicitly set to 'off' without TODO comment + issue link
- ❌ // eslint-disable-next-line without accompanying TODO + issue
- ❌ Missing ESLint/Prettier/CI/husky config files when project has package.json
- ❌ Vite config with minify:'terser' but no drop_console/drop_debugger/manualChunks

## Type Safety Anti-patterns (TS/JS)
- ❌ (window as unknown as Record<string, unknown>) global exposure
- ❌ any / as any / <any>
- ❌ @ts-ignore / @ts-expect-error without issue link in comment
- ❌ Default exports (use named exports)

## Architecture Anti-patterns
- ❌ UI layer exposing methods via window globals (must use EventBus)
- ❌ Renderer using independent requestAnimationFrame (must go through main loop update(dt))
- ❌ main.ts directly calling Render layer methods (must go through EventBus)
- ❌ Core layer importing three / document / window (must be environment-agnostic)

## Implementation Anti-patterns (defeats "form compliance trap")
- ❌ Empty function body ({} or only console.log) without TODO
- ❌ Hook empty implementation (e.g., onPlacement directly return scores)
- ❌ Class name promising capability but no implementation (e.g., PostProcessing class without EffectComposer)
- ❌ File exists but content is Stub (unless doc explicitly allows placeholder)

## Integration Anti-patterns
- ❌ init() method defined but never called in any bootstrap path
- ❌ loadSounds()/loadAssets() method exists but not called in bootstrap
- ❌ Event emit without any matching on/subscribe
- ❌ manifest.json referencing non-existent resource files

## Python-Specific (extends contexts/python.md)
- ❌ import * (use explicit imports)
- ❌ eval() / exec()
- ❌ bare except: (use specific exceptions)
- ❌ os.system() (use subprocess with list args)
- ❌ Non-atomic file writes for persistent state (use tmp + os.replace)
- ❌ Hardcoded Windows paths (use sys.executable or pathlib)
- ❌ requests library in core modules (use urllib.request)
```

**Integration**: `context.py::suggest_contexts` already returns contexts based on detected languages; add `"anti-patterns"` to always be included when any code language is detected. One-line change in `context.py`.

**Validation**: Run 5 coding tasks with/without the prompt (A/B via `experiments.py`). Expected: review-risk agent finds fewer "explicit constraint bypass" findings.

**Files to create**:

**Content structure**:
```
---
description: Naming contract enforcement — doc names are non-negotiable
priority: 92
version: 2.0.0
trigger: when spec/design doc (.md) is in working set OR .ts/.tsx files touched
---
# Naming Contract (enforced)

## Principle
Names in spec/design docs are CONTRACTS, not suggestions. Before implementing any
class/method/interface/event/enum, search the doc for the canonical name. If the doc
names it, you MUST use that exact name. No "I prefer my convention."

## Doc-Aware Implementation Rule
1. Before writing any new class/method, grep the spec doc for candidate names
2. If doc has explicit name → use it verbatim (case-sensitive)
3. If doc is silent → follow language convention (PascalCase/camelCase/UPPER_SNAKE)
4. NEVER invent a synonym because "it reads better" — doc wins

## Common Drift Patterns (banned)
| Doc Name | Banned Variant | Why Drift Happens |
|----------|----------------|-------------------|
| GameState | GamePhase | "phase sounds more accurate" — no, doc wins |
| ScoreState | ScoreData | "data is more common" — no, doc wins |
| generateBlock | addNextBlock | "add is simpler" — no, doc wins |
| game:stateChange | state:changed | "shorter is cleaner" — no, doc wins |
| SoundManager | AudioManager | "audio is more general" — no, doc wins |

## Self-Check Before Committing
- [ ] Every class name in my code appears verbatim in the spec doc OR follows convention for unnamed concepts
- [ ] Every public method name matches doc OR is clearly an internal helper (prefixed _)
- [ ] Every event name matches doc's event section
- [ ] Every enum value matches doc's enum section
```

**Integration**: Extend `context.py::detect_file_directory` to recognize `*/specs/`, `*/docs/`, `*.spec.md`, `*design*.md` as "contract docs present" signal → auto-load naming-contract context.

**Validation**: Re-run a Tower Stack 3D module (e.g., StackEngine) with the prompt. Expected: 0 naming drifts vs current ~50%.

```
---
description: Test quality gate — no soft assertions, boundary coverage required
priority: 88
version: 2.0.0
trigger: when test files (*.test.ts, *.spec.ts, test_*.py, *_test.py) are touched
---
# Test Quality Gate (enforced)

## Banned Soft Assertion Patterns
- ❌ expect(array).toContain(knownValue) — for known values, use toBe or toEqual
- ❌ expect(result).toBeTruthy() — too lenient, use semantic assertion
- ❌ expect(result).toBeDefined() — too lenient
- ❌ expect(result).toBeGreaterThan(0) when 0 is the only impossible value — meaningless

## Required Precise Assertions
- ✅ expect(result).toBe(expectedExactValue)
- ✅ expect(result.score).toBe(42) — exact
- ✅ expect(result.state).toBe('playing') — exact enum

## Boundary Coverage Rule
For any threshold/saturation/临界值, MUST test three tiers:
- threshold − 0.1% (just below)
- threshold exact (at boundary)
- threshold + 0.1% (just above)

## Project-Specific Boundaries (extend per project)
Generic list — projects add their own:
- [ ] Zero-boundary: count = 0 / -1 (negative)
- [ ] Saturation: at max / max+1
- [ ] State machine: all illegal transitions
- [ ] localStorage unavailable → fallback
- [ ] Async rejection paths

## Coverage Configuration Rule
- vitest.config.ts coverage.thresholds MUST be set (statements/branches/functions/lines ≥ 85%)
- coverage.include MUST be ['src/**/*.ts'] (full source), NEVER ['src/core/**/*.ts'] (partial)
- Test files use .test.ts (project convention) — never mix .test.ts and .spec.ts in same project

## Test Self-Check
- [ ] No soft assertions in new tests
- [ ] Every threshold has 3-tier boundary tests
- [ ] Coverage thresholds configured
- [ ] Coverage scope is full src/, not partial
```

## 6. Risk Analysis & Mitigation

### 6.1 Prompt Overload Risk (from source Section 6.1)

**Risk**: 5+ new context prompts (anti-patterns, naming-contract, test-quality, flash-role, ui-components) may bloat the composed prompt and degrade deepseek output.

**Mitigation**:
- Context prompts use `priority` for layering — only relevant contexts load (e.g., `test-quality` only when test files touched, not always)
- `context.py` detection is the gatekeeper — a coding task on `src/core/StackEngine.ts` loads `anti-patterns + naming-contract + typescript + flash-role` (4 contexts), not all 5
- Each context prompt is ≤ 50 lines, compressed table format
- A/B test token usage via `experiments.py tokens_used` field — if composed prompt > 8K tokens, trim

### 6.2 Skill False Positive Risk (from source Section 6.2)

**Risk**: Integration-link-checker may flag legitimate patterns (e.g., init called via indirect reference, event subscribed via decorator).

**Mitigation**:
- All skills output `error` (must fix) vs `warning` (suggest verify) distinction
- `.opencode/integration-whitelist.json` allows user-marked "confirmed safe" items
- Skills NEVER auto-fail delivery on warnings — only on errors
- First 2 weeks of use: all findings are warnings, promote to errors after confidence builds

### 6.3 Flash Guard Over-Restriction Risk

**Risk**: Migrating `planner.py` to Pro may increase cost and latency for deep search.

**Mitigation**:
- `planner.py` already has `planner_mode` parameter (flash/pro) — make `pro` the default, `flash` the opt-in for cost-sensitive use
- `aggregator.py` stays on Flash (utility, has reliable fallback)
- A/B test: measure Deep Search success rate with Pro planner vs Flash planner — if Pro is < 10% better, revert
- Cost monitoring via existing `experiments.py tokens_used` field

### 6.4 Model Iteration Invalidation Risk (from source Section 6.3)

**Risk**: DeepSeek V5 release may make these prompts/skills unnecessary or counterproductive.

**Mitigation**:
- All prompts/skills designed around **doc-contract + anti-pattern** principles, not model-specific quirks
- Tower Stack 3D serves as regression test — re-run on model upgrades
- `experiments.py` A/B data shows which prompts/skills are pulling weight — retire ones with negligible effect

### 6.5 Conflict with Original ROADMAP Risk

**Risk**: This plan abandons V1.6-V2.5 mainline. If those features (multi-agent, self-evolution) become needed later, the work is wasted.

**Mitigation**:
- This plan **augments** the discipline foundation; it does not delete the original ROADMAP
- V1.6 stabilization bugs (B1-B6) are fixed here as Phase 0 — they were V1.6 P0-1/P0-2/P1-1 anyway
- V1.7 ChromaDB vector retrieval can still proceed later — it's orthogonal to coding discipline
- V2.0 Multi-Agent REQUIRES disciplined single-agent first; this plan IS the prerequisite
- Original ROADMAP files preserved as reference; this plan is the active path until discipline targets are met

### 6.6 Scope Creep Risk

**Risk**: 8 directions + 6 bug fixes + 24 new files is large scope; may stall mid-execution.

**Mitigation**:
- Phased delivery with strict exit criteria per phase
- Phase 0 (5 days) is fixed and small
- Phase 1 (1-2 weeks) delivers 3 prompts with immediate measurable effect — early win builds momentum
- Phase 2 (2-3 weeks) is the riskiest (architecture change) — can pause after Phase 1 if needed
- Phase 3 (3-5 weeks) skills are independent — can ship 3A, then 3B, then 3C, then 3D separately
- Each phase's exit is a usable state, not a partial state
