# 2.0 Lightweight Multi-Agent Kernel Contracts and State

Status: conceptual planning contract. No Python implementation, schema, migration,
or runtime behavior is created by this document.

## 1. Contract rules

The 2.0 domain model is framework-neutral. Persisted records use stable project
identifiers and normalized enums, not OpenAI Agents SDK or PydanticAI objects.
All timestamps are UTC. Identifiers are opaque and immutable. Metadata is bounded
and must not contain Secrets, raw prompts, raw model responses, cookies, private
Memory, or unrestricted tool output.

Every mutable record carries a version or compare-and-set token so concurrent
writers cannot silently overwrite each other. Terminal transitions are
append-audited through existing Run/Step/Event mapping.

## 2. Task

A `Task` is the authoritative unit of Kernel work.

Required conceptual fields:

| Field | Meaning |
|---|---|
| `task_id` | immutable unique identifier |
| `parent_task_id` | optional parent for bounded decomposition |
| `objective` | concise user-approved purpose |
| `normalized_input` | typed, bounded input after validation and redaction |
| `status` | Task state defined below |
| `owner_agent_id` | current Agent owner or null while queued/terminal |
| `required_capabilities` | Registry-aligned capability requirements |
| `budget` / `budget_used` | immutable initial limits and current ledger |
| `current_step` | current logical step/checkpoint reference |
| `artifact_ids` | references only; Artifact content is not embedded |
| `approval_ids` | Approval references relevant to the Task |
| `run_id` | correlation to existing Run/Step/Event telemetry |
| `created_at`, `updated_at`, `started_at`, `finished_at` | UTC lifecycle timestamps |
| `failure` | optional normalized failure category and redacted detail |
| `degraded` | optional usable-result limitations and missing capabilities |
| `idempotency_key` | caller-scoped duplicate-creation protection |
| `record_version` | optimistic concurrency token |

Invariants:

- `objective` and normalized input are validated before persistence.
- A child Task cannot receive more budget or permissions than the parent makes
  available.
- A terminal Task has `finished_at` and cannot return to a non-terminal state.
- `succeeded` requires accepted required Artifacts and satisfied required
  Approvals; `degraded` requires usable output plus explicit limitations.
- Task records never become a storage location for model conversation history.

## 3. AgentSpec

`AgentSpec` declares what an Agent may do; it is not a mutable runtime identity.

Required conceptual fields:

| Field | Meaning |
|---|---|
| `agent_id` | stable identifier for the specification |
| `role` | Coordinator, Worker, or combined Reviewer/Tester in 2.0 |
| `capabilities` | declared capability names/versions |
| `allowed_tools` | explicit tool/capability allowlist |
| `model_policy` | Gateway task class/model policy reference, never an endpoint |
| `permission_scope` | Workspace, network, Memory, subprocess, and publication limits |
| `max_concurrency` | finite simultaneous execution limit |
| `budget_limits` | per-invocation and aggregate ceilings |
| `input_contract` | accepted typed input shape/version |
| `output_contract` | required typed result shape/version |
| `enabled` | whether new work may be assigned |
| `spec_version` | immutable revision identifier |

Invariants:

- Handoff cannot widen the target AgentSpec permission scope.
- Tool names resolve through maintained capability adapters; arbitrary callable
  import paths are not accepted.
- Model policy resolves through `modules.dispatch.gateway`; no AgentSpec stores
  a Provider URL or Secret.
- Reviewer/Tester cannot silently modify a Worker Artifact; it produces a typed
  decision and bounded feedback.

## 4. Handoff

A `Handoff` is an explicit persisted transfer of ownership. Agent-as-tool is not
a Handoff: in Agent-as-tool the caller remains owner and receives a typed result.

Required conceptual fields:

| Field | Meaning |
|---|---|
| `handoff_id` | immutable identifier |
| `task_id` | owning Task |
| `source_agent_id` | current owner requesting transfer |
| `target_agent_id` | intended next owner |
| `reason` | bounded structured reason |
| `context_ref` | bounded context reference or redacted payload |
| `expected_artifact` | expected Artifact type/contract |
| `acceptance_criteria` | explicit, testable completion criteria |
| `budget_transfer` | budget reserved for target execution |
| `status` | Handoff state defined below |
| `idempotency_key` | duplicate creation/consumption protection |
| `created_at`, `accepted_at`, `consumed_at`, `finished_at` | UTC timestamps |
| `record_version` | optimistic concurrency token |

Invariants:

- Source must own the Task when requesting the Handoff.
- Budget transfer is reserved atomically and cannot exceed remaining parent
  budget.
- Acceptance transfers Task ownership exactly once.
- Context is minimum necessary and excludes Secrets/private Memory unless a
  separately approved scoped reference is allowed.
- Rejection leaves ownership with the source and records the reason.

## 5. Artifact

An `Artifact` is an immutable logical output identity. New bytes or validation
results create a new revision or explicit supersession; silent overwrite is
forbidden.

Required conceptual fields:

| Field | Meaning |
|---|---|
| `artifact_id` | immutable identifier |
| `task_id` | producing Task |
| `producer_agent_id` | producing Agent |
| `handoff_id` | optional originating Handoff |
| `artifact_type` | typed category such as text patch, report, or test result |
| `reference` | Workspace-relative path or bounded logical reference |
| `digest` | content digest and algorithm |
| `provenance` | source inputs, tool/step references, and producer version |
| `created_at` | UTC creation timestamp |
| `validation_status` | Artifact state defined below |
| `sensitivity` | public/project/private/secret-prohibited classification |
| `retention` | lifecycle/cleanup policy |
| `supersedes_artifact_id` | optional explicit replacement link |
| `record_version` | optimistic concurrency token |

Invariants:

- Paths resolve inside the assigned Workspace and are stored in normalized form.
- Digest is calculated after atomic materialization and before registration.
- A changed file cannot retain the same Artifact identity.
- Artifact metadata does not embed unrestricted content.
- Secret-classified content is rejected from general Artifact registration;
  approved private references use the existing private storage boundary.

## 6. Approval

An `Approval` is a scoped, auditable decision, not a general role grant.

Required conceptual fields:

| Field | Meaning |
|---|---|
| `approval_id` | immutable identifier |
| `task_id` | related Task |
| `requested_action` | exact normalized action and target/digest |
| `reason` | why Approval is required |
| `scope` | permissions granted if approved |
| `requester_agent_id` | requesting Agent |
| `decision` | pending/approved/denied/expired/cancelled |
| `decision_maker` | authenticated human or named policy boundary |
| `requested_at`, `decided_at` | UTC timestamps |
| `expires_at` | mandatory when the grant is time-sensitive |
| `consumed_at` | when a single-use Approval is used |
| `audit_reference` | Run/Event or external review reference |
| `record_version` | optimistic concurrency token |

Invariants:

- Decision compares against the exact requested action and Artifact digest.
- Approved scope cannot exceed the request.
- Denied, expired, cancelled, or already consumed Approval cannot authorize work.
- One atomic compare-and-set decides the request; later decisions are conflicts.
- Ordinary read-only local work does not require ceremonial Approval.

## 7. Budget

A Budget has finite non-negative limits for:

- logical steps;
- input/output/total tokens, using Gateway usage when available;
- wall-clock deadline and/or duration;
- retries;
- tool calls;
- concurrently/total participating Agents;
- child Task count.

Conceptual representation:

```text
BudgetLimit        immutable initial ceilings
BudgetReservation  amount reserved for a child/Handoff
BudgetUsage        append-audited actual consumption
BudgetSnapshot     remaining values at a checkpoint
```

Semantics:

1. **Consume:** charge at the defined boundary exactly once. Model usage is
   reconciled from Gateway metadata; a missing usage value is represented as
   unknown and handled by policy, never assumed zero.
2. **Inherit:** a child receives a subset of the parent's remaining limits.
3. **Transfer:** a Handoff atomically reserves budget from the source Task and
   makes only that reservation available to the target.
4. **Release:** unused reservation may return only under an explicit rule before
   terminal accounting; consumed budget is never refunded.
5. **Exhaust:** no new protected operation starts. The Task becomes failed,
   timed out, or degraded according to whether a usable accepted result exists
   and which budget was exhausted.
6. **Retry composition:** Gateway retry policy and selected Executor retry
   behavior must not multiply. One layer is authoritative for each operation.

## 8. State machines

### 8.1 Task

States:

- `queued`
- `running`
- `waiting_approval`
- `handoff_pending`
- `reviewing`
- `succeeded`
- `degraded`
- `failed`
- `cancelled`
- `timed_out`
- `abandoned`

Allowed conceptual transitions:

```text
queued -> running | cancelled | timed_out
running -> waiting_approval | handoff_pending | reviewing
running -> succeeded | degraded | failed | cancelled | timed_out | abandoned
waiting_approval -> running | failed | cancelled | timed_out | abandoned
handoff_pending -> running | failed | cancelled | timed_out | abandoned
reviewing -> running | succeeded | degraded | failed | cancelled | timed_out
```

Rules:

- `succeeded`, `degraded`, `failed`, `cancelled`, `timed_out`, and `abandoned`
  are terminal.
- Returning from `reviewing` to `running` requires remaining retry/rework budget.
- `abandoned` means ownership cannot safely continue within 2.0; it does not
  claim 2.1 durable recovery.
- A state change and its checkpoint/event are committed atomically where they
  belong to the same authority transaction.

### 8.2 Handoff

States:

```text
requested -> accepted -> consumed -> completed
requested -> rejected | cancelled | expired
accepted -> cancelled | expired
consumed -> completed | failed | cancelled | timed_out
```

Only `accepted -> consumed` transfers ownership, and it occurs once. Terminal
states are completed, rejected, failed, cancelled, expired, and timed_out.

### 8.3 Artifact

States:

```text
declared -> materialized -> validating -> accepted
                         -> rejected
                         -> degraded
materialized -> invalidated
accepted/degraded -> superseded
```

Artifact bytes are immutable after materialization. Supersession creates a new
Artifact and link; it does not rewrite history.

### 8.4 Approval

States:

```text
pending -> approved -> consumed
pending -> denied | expired | cancelled
approved -> expired | cancelled
```

Approved scope may be single-use or bounded multi-use only when explicitly
modeled. Terminal decision history is append-audited.

## 9. SQLite authority

SQLite is the planned Task/checkpoint authority. The physical database path is a
Slice 0/1 ADR decision. Sharing `_runtime/mcp-sqlite.db` is permissible only if
reviewed operational requirements support it; separate tables, migrations,
transactions, and ownership semantics are mandatory either way.

Kernel authority includes only:

- Task identity, state, owner, and versions;
- checkpoints and claim/lease data;
- Handoff, Artifact, and Approval records;
- budget reservations/usage;
- idempotency and audit correlation needed for Kernel recovery semantics.

It must not blur or replace:

| Existing domain | Existing authority meaning |
|---|---|
| Scheduler jobs/runs | when a scheduled job should run and each job attempt |
| Search cache | Provider/final Search result caching and migration ledger |
| Memory candidates | approval-gated candidate lifecycle and durable Memory boundary |
| Runtime Supervisor ownership | which local service process is owned/adopted and may be stopped |

A Scheduler run may create a Kernel Task through an idempotent adapter, but the
Scheduler remains authority for scheduling and the Kernel remains authority for
Task execution. Run/Step/Event remains telemetry, not Task state authority.

## 10. Transactions, concurrency, and idempotency

### Task duplicate protection

- Caller supplies a scoped idempotency key for creation.
- A unique constraint maps the key to one Task and returns the original result
  on safe replay.
- Claiming uses a transaction plus record version/lease so only one executor
  owns a runnable Task.
- Lease expiry does not imply safe replay of side effects; reconciliation decides
  failed/abandoned behavior within the 2.0 boundary.

### Handoff duplicate protection

- Creation and consumption each have stable idempotency keys.
- Acceptance/consumption use compare-and-set state transitions.
- Duplicate consumers receive the original outcome or a deterministic conflict;
  they never repeat the Worker side effect.

### Approval duplicate protection

- One pending Approval can receive one atomic decision.
- Repeated identical requests may resolve to the original record when action,
  scope, target, and digest match.
- Changed action/digest requires a new Approval.

### Artifact collision protection

- Reference plus expected previous digest/version prevents silent overwrite.
- Materialization uses a temporary file and atomic replace where supported.
- Registration fails if bytes, digest, Task, producer, or path preconditions do
  not agree.

### Crash boundary: 2.0 versus 2.1

2.0 persists committed state and can reconcile obvious queued/claimed records,
but it does not promise transparent replay of arbitrary in-flight tool work or a
full Git worktree rollback. After uncertain side effects it records failed or
abandoned state and requires explicit review. Durable pause/resume, per-step
worktree recovery, and bounded rollback are 2.1.

## 11. Failure semantics

| Category | Meaning | Typical Task outcome |
|---|---|---|
| validation failure | input/contract/state transition invalid before execution | failed; no side effect |
| configuration failure | required local configuration or Adapter missing/invalid | failed or capability unavailable |
| Provider unavailable | Gateway reports required Provider not ready/reachable | failed for required model; degraded/unavailable for optional capability |
| execution failure | Agent/tool operation ran and failed | failed unless accepted usable partial result exists |
| timeout | deadline or operation timeout reached | timed_out |
| cancellation | authenticated cancellation requested/propagated | cancelled |
| budget exhaustion | next operation would exceed a finite limit | failed/timed_out/degraded according to usable accepted result |
| approval denied | protected action explicitly denied | failed or cancelled by policy; action not executed |
| partial/degraded result | usable accepted result with stated missing evidence/capability | degraded |
| abandoned work | ownership/recovery is uncertain and 2.0 cannot safely continue | abandoned |

Rules:

- A caught exception is not automatically degraded; degraded requires usable
  output and explicit limitations.
- Provider errors retain normalized category, retryability, and redacted detail.
- No path converts unavailable, timeout, denied, or empty output into success.
- Failure records contain references and bounded diagnostics, not raw sensitive
  payloads.

## 12. Mapping to Run/Step/Event

The Kernel reuses the existing telemetry envelope:

| Domain object/activity | Mapping |
|---|---|
| Task lifecycle | one correlated Run with `task_id`; terminal reduction agrees with Task state |
| Agent execution | Step with `agent_id`, role, attempt, parent Task, and bounded usage |
| model/tool operation | child Step/Event through Gateway or capability Adapter |
| Handoff | requested/accepted/rejected/consumed/completed Events and target execution Step |
| Artifact | declared/materialized/validated/accepted/rejected Events with ID/digest only |
| Approval | requested/approved/denied/expired/cancelled/consumed Events |
| Budget | usage/reservation/exhaustion Events and bounded snapshots |
| failure/degraded/cancel/timeout/abandon | normalized Events and terminal Run reduction |

Task SQLite records remain authoritative even if telemetry writing is degraded.
Telemetry failure is visible and may block release evidence, but it cannot cause
a second state machine to take ownership. Executor traces are optional external
references only; remote tracing and sensitive capture are disabled by default.

## 13. Open decisions and gates

Implementation cannot begin until reviewers decide:

1. the exact Task state transition table and terminal reduction precedence;
2. the physical SQLite path, schema ownership, migration/versioning, WAL and
   transaction policy;
3. claim/lease semantics and what 2.0 marks `abandoned` after a crash;
4. the minimum AgentSpec permission vocabulary and tool capability naming;
5. budget charging boundaries, token-unknown policy, and retry ownership;
6. Approval levels and which actions require human decision;
7. Artifact path, digest, supersession, sensitivity, and retention policy;
8. Agent-as-tool versus Handoff selection rules;
9. the exact Run/Step/Event correlation fields;
10. the deterministic first E2E Task and its acceptance fixture.
